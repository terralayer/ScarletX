# ScarletX 0.3.10 Packaging and Deployment Results

Date: 2026-09-02

## Scope

Task 10 measured the packaging/deployment changes in PR #38 against the PR 9 merge baseline `34d7c27b44a8c4591eff313feee4fc209c4ec6cd`. The authoritative runtime comparison was executed on one GitHub-hosted Ubuntu 24.04 runner so both revisions saw the same host conditions. The comparison evidence head was `a495716310e3e7ec7e7b297fa076da64172ba261`.

The optimized packaging keeps the required repair/extract/probe utilities, non-root UID/GID 568 runtime, persistent `/config`, `/downloads`, `/media`, and `/backups` paths, private backend networking with explicit backend egress, and a public web proxy. Base images are digest pinned and the runtime backend no longer copies release-only documentation.

## Reproducible build and validation commands

From a clean checkout with Docker available:

```bash
docker build -f Dockerfile -t scarletx-backend:candidate .
docker build -f Dockerfile.web -t scarletx-web:candidate .

docker compose -f docker-compose.yml config
docker compose -f docker-compose.truenas.yml config

docker image inspect scarletx-backend:candidate --format '{{.Size}}'
docker image inspect scarletx-web:candidate --format '{{.Size}}'

docker save scarletx-backend:candidate | gzip -1 | wc -c
docker save scarletx-web:candidate | gzip -1 | wc -c
```

To collect exact cgroup memory after the container is healthy and idle:

```bash
docker exec <backend-container> cat /sys/fs/cgroup/memory.current
docker exec <web-container> cat /sys/fs/cgroup/memory.current
```

Cold-health timing is measured from `docker run` until the corresponding `/api/health` request succeeds. The authoritative A/B run alternated PR9 and PR10 seven times for each backend and web image and compared medians.

The permanent release workflow also validates both Compose files, confirms `par2`, `ffprobe`, `7z`, and `unrar` are present, records image sizes, and smoke-tests the candidate health path before publishing images. Anonymous release-image pulls and the TrueNAS validation path remain in the release gate.

## Upgrade and rollback evidence

The upgrade proof used the released `ghcr.io/terralayer/scarletx:0.3.9` image, not a reconstructed source approximation:

1. Boot the released 0.3.9 image and create its real SQLite schema.
2. Insert a real `Scene` ORM record.
3. Create and persist the ScarletX encryption key and verify mode `0600`.
4. Preserve a complete pre-upgrade `/config` snapshot and hashes.
5. Boot the PR10 candidate against the populated 0.3.9 state and verify the record remains readable and the secret key remains unchanged.
6. Restore the preserved pre-upgrade `/config` snapshot.
7. Boot the released 0.3.9 image again and verify the record plus encryption/decryption roundtrip.

All upgrade and rollback checks passed.

During this proof, an existing-database startup path exposed a packaging defect: the default backup directory was relative (`./backups`) while the non-root container runtime mounted persistent `/backups`. PR10 fixed this at the product boundary. Local development still defaults to `./backups`, while packaged containers explicitly default to persistent `/backups`; a regression test locks that behavior.

For an operator rollback:

1. Stop ScarletX and preserve the entire `/config` directory before upgrade, including `/config/.scarletx-secret.key`.
2. Keep the pre-upgrade snapshot unchanged while validating the new image.
3. If rollback is required, stop the candidate, restore the preserved pre-upgrade `/config` snapshot, and run the prior 0.3.9 image.
4. Keep `/backups` persistent and do not regenerate or replace the secret key independently of its matching database/config state.
