# ScarletX 0.3.10 Performance Baseline

This document records the reproducible baseline for the ScarletX 0.3.10 whole-app optimization series. Later optimization PRs must reuse these scenarios and fixed fixture sizes so before/after comparisons remain meaningful.

## Measurement contract

Command:

```bash
python tools/benchmark_0310.py --scenario all --iterations 5 --json /tmp/scarletx-0310-baseline.json
```

The harness uses only generated temporary SQLite databases, generated local files, and an injected in-memory HTTP transport. It does not read a user's ScarletX database, media tree, TPDB API key, or live network service.

Each scenario records five timed samples and reports the median. These CI-runner measurements are comparison baselines for the 0.3.10 optimization work, not production latency SLAs.

## Baseline result

Reference measurement: GitHub Actions `Tests` run 181 (`33532290885`), benchmark job `99938264883`, measured from PR 1 implementation commit `1d480e5e974511f0ad32a3180c14acea88a9c72a` on 2026-09-01.

| Scenario | Fixed fixture | Median | Throughput | Baseline observation |
| --- | --- | ---: | ---: | --- |
| `list_api` | 1,000 scenes; first page of 100 | 0.007412721 s | 13,490.32 rows/s | Existing scene-list serialization baseline. |
| `library_scan` | 10,000 files in 100 directories; warm scan first | 1.429299743 s | 6,996.43 files/s | An unchanged tree still traverses/processes all 10,000 files. |
| `queue_reads` | 200 native Usenet jobs | 0.003754726 s | 53,266.20 rows/s | Existing queue serialization baseline. |
| `tpdb_coalescing` | 100 concurrent equivalent reads | 0.045866323 s | 2,180.25 reads/s | 100 equivalent reads produced 100 transport calls in every sample; no request coalescing is present yet. |

## Acceptance use in later PRs

- PR 2 compares `list_api` against the 7.41 ms median while also proving constant query counts and index use.
- PR 3 must reduce 100 equivalent concurrent TPDB reads from 100 transport calls to exactly 1 while preserving correctness and bounded memory.
- PR 4 reuses `queue_reads` to ensure persistence throttling does not regress live queue reads.
- PR 5 compares an unchanged 10,000-file scan against the 1.429 s full-scan median and must avoid repeated probing/work for unchanged files.

Any future fixture or semantic change must be documented separately rather than silently replacing this baseline.
