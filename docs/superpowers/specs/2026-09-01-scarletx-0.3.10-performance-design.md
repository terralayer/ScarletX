# ScarletX 0.3.10 Performance Release Design

## Purpose

ScarletX 0.3.10 reduces idle database traffic, repeated filesystem work, duplicate metadata requests, and redundant media processing without changing the supported deployment architecture. Development remains isolated from `main` and moves through `0.3.10-beta.1`, `0.3.10-beta.2`, and `0.3.10-beta.3` before the final release.

The completed status console from `feature/status-console` is the starting point for this release line. It remains operationally read-only: console reporting must never make health checks or worker state transitions fail.

## Release Boundaries

- `main` remains the stable `0.3.9` line until all three betas pass.
- Beta 1 establishes the performance architecture and ships the highest-value optimizations.
- Beta 2 fixes defects and compatibility issues found while exercising Beta 1 on real libraries and download queues.
- Beta 3 is a release candidate: only regression fixes, dependency fixes, documentation, and release metadata may change.
- Final `0.3.10` is promoted from the verified Beta 3 code; it does not receive new features.
- Existing databases, encrypted credentials, media paths, download queues, TrueNAS storage, and Docker Compose deployments must upgrade in place.
- FastAPI remains private on port 8000; Nginx remains the sole public entrypoint.

## Delivery Workflow

Each numbered optimization is developed on its own feature branch created from the current
`release/0.3.10` head. Each branch receives focused tests and before/after measurements, then opens a
separate pull request whose base is `release/0.3.10`. A stage is merged only after its focused checks and
the full test suite pass. The feature branch is deleted after merge, and the next stage starts from the
updated release branch.

No optimization implementation is committed directly to `release/0.3.10`. Documentation-only release
coordination may use the release branch, but changes to runtime code, templates, migrations, dependencies,
or tests follow the per-stage pull-request workflow. If a stage does not improve its declared measurement
or creates an unacceptable regression, its PR is not merged.

## Recommended Architecture

The release uses focused, independently testable optimizations rather than a worker/API process split. The process split remains a future architectural release because it would enlarge the migration and operational risk of 0.3.10.

### 1. Incremental library scanner

The filesystem watcher becomes the normal change source. A thread-safe dirty-directory queue coalesces repeated events for the same directory. The scanner drains a bounded snapshot of dirty directories and scans them with `os.scandir()`. It fingerprints or probes a file only when its stored size or modification time differs.

A full recursive scan remains available for first startup, explicit manual scans, recovery after watcher overflow, and a low-frequency reconciliation run. Full scans also use `os.scandir()` so the old `Path.rglob()` hot path is removed.

Scanner state is stored in SQLite so a restart does not force unchanged files through probing. State records contain the normalized path, size, nanosecond mtime when available, and last successful scan time. Missing files are reconciled only within directories included in the current scan scope.

Errors are isolated per directory and per file. An unreadable directory produces a warning/status event and stays dirty for a later retry; it does not abort the entire scan.

### 2. Global queue event stream

One global SSE connection supplies the queue badge, progress, speed, ETA, failure counts, post-processing transitions, and import completion. The server publishes monotonic event IDs and compact typed events. The client reconnects using `Last-Event-ID`; if the replay window is unavailable, the server sends one fresh snapshot before resuming deltas.

Normal UI polling is removed. A slow or disconnected browser cannot block workers: publishing writes to a bounded in-memory replay buffer, and each subscriber has a bounded queue. Overflow causes a snapshot resynchronization rather than unbounded memory growth.

SSE authentication continues to use the existing same-origin session mechanism. No secrets or exception bodies are included in events.

### 3. Progress persistence throttling

Live byte counts, speed, and ETA remain in memory and feed SSE directly. SQLite receives progress checkpoints no more often than every two seconds per active job or after a meaningful byte threshold, whichever occurs first. State transitions, terminal counters, failures, and shutdown checkpoints are always persisted immediately.

After a restart, the UI may temporarily display the latest persisted checkpoint, but job state and final counters must remain correct. The persistence throttle must not delay cancellation, retry, completion, or failure transitions.

### 4. Query-focused database indexes

Schema migration adds composite indexes for the worker queries confirmed by `EXPLAIN QUERY PLAN`:

- `native_usenet_jobs(status, created_at)`
- `native_usenet_jobs(status, updated_at)`
- `tracked_downloads(status, created_at)`
- `tracked_downloads(status, last_checked_at)`
- `background_jobs(status, kind, created_at)`
- `history(event_type, created_at)`

Migration is idempotent and uses the existing pre-migration backup mechanism. Tests must show the intended queries use the new indexes and an existing 0.3.9 database upgrades without data loss.

### 5. TPDB memory cache and request coalescing

TPDB reads follow `memory LRU -> existing disk cache -> network`. The memory cache is bounded to 512 entries and uses the existing disk-cache TTLs. Concurrent equivalent requests share one in-flight task. Failures are delivered to all waiters but are never cached as successful results, and cancellation by one waiter does not cancel the shared request for others.

Cache keys include every request parameter that changes the response. Credential values and authorization headers are excluded from logs and status events.

### 6. Lightweight list APIs

Scene, performer, and studio list endpoints use explicit summary projections rather than loading detail relationships. Each summary contains only fields required by the corresponding card/table UI. Detail endpoints retain the complete response.

Query-count regression tests set a fixed upper bound independent of page size, preventing N+1 relationship loads. Response compatibility is preserved for fields the current frontend actually consumes; unused detail-only fields are removed from list payloads only after frontend contract tests demonstrate they are not required.

### 7. Duplicate media-processing suppression

Successful imports register the destination path plus stable file identity in a bounded, expiring in-memory registry. Watcher/scanner work consults that registry before scheduling ffprobe, fingerprinting, or artwork generation. Suppression applies only when path, size, and modification identity match; a genuinely modified file is processed normally.

The registry is an optimization, not persisted state. Restarting ScarletX can cause one harmless recheck but cannot cause a file to be skipped permanently.

### 8. Download and post-processing pipeline

The native Usenet pipeline is measured by receive, decode, write, verify, repair, extract, probe, and import
phase before concurrency changes are made. Optimizations use bounded queues and explicit backpressure so a
fast upstream phase cannot create unbounded memory use or starve API work. Concurrency remains configurable
within safe limits, cancellation reaches every phase, and partial files retain the current recovery behavior.

Provider selection, connection reuse, and retry behavior are changed only when measurements identify them
as bottlenecks. Repair, extraction, and media probing continue to use mature system tools. A failed phase
records a specific terminal reason without leaking credentials or command output containing secrets.

### 9. Backend and frontend decomposition

Large modules are split only after their public behavior is covered by tests. `scarletx/main.py` is reduced
to application composition and router registration; domain routes and orchestration move into focused
modules. `scarletx/native_usenet.py` is separated along queue, transport, persistence, and post-processing
boundaries without changing its stored job model or recovery semantics.

The monolithic `frontend/index.html` is decomposed into static markup and focused same-origin JavaScript and
CSS assets. The browser continues to require no Node.js runtime or client build step in production. Existing
routes, element contracts, authentication redirects, accessibility behavior, and responsive layouts remain
compatible throughout the split.

Structural changes must be behavior-neutral. They are accepted for reduced coupling, smaller review units,
and easier profiling; they are not allowed to conceal feature changes or speculative abstractions.

### 10. Packaging and deployment optimization

Backend and web images remove unused runtime configuration and packages only after verifying required repair,
extraction, probing, and health-check tools. Layer ordering maximizes dependency reuse without weakening
version pinning or anonymous pulls. Startup avoids repeatable initialization work that can safely be deferred
or skipped, while migrations and secret creation remain blocking and durable.

Docker Compose and TrueNAS keep the two-container Nginx/backend architecture, explicit internal networking,
non-root runtime identities, storage compatibility, and lightweight health checks. Image size, cold startup,
steady-state memory, rendered TrueNAS output, upgrade, and rollback are recorded before and after changes.

## Deferred Work

Provider EWMA scoring, WebP artwork generation, and splitting heavy workers into a separate process remain
deferred. They may enter a later release only through a separately approved design. The download-pipeline
work in this release may introduce bounded phase queues, but it does not create a new worker process or alter
the supported deployment topology.

## Testing and Measurements

Every behavior change follows red-green-refactor tests. Required coverage includes:

- Dirty-directory coalescing, scoped deletion reconciliation, watcher overflow, restart state, and unchanged-file probe avoidance.
- SSE snapshot, delta, replay, overflow resynchronization, authentication, and subscriber isolation.
- Progress checkpoint timing plus immediate transition/final persistence.
- Migration from a populated 0.3.9 SQLite fixture and query-plan index assertions.
- TPDB LRU eviction, TTL handling, coalesced concurrent success/failure, and waiter cancellation.
- Fixed query-count tests for list endpoints at small and large page sizes.
- Import/watcher duplicate suppression and changed-file bypass.
- Per-phase download throughput, bounded backpressure, cancellation, recovery, and failure propagation.
- Route-registration, job-recovery, and browser-contract tests before and after module decomposition.
- Backend/web image size, cold startup, steady-state memory, TrueNAS rendering, upgrade, and rollback checks.

Before each beta, run the full Python 3.11/3.12/3.13 matrix, dependency audit, source compilation, backend and Nginx container builds, TrueNAS rendering, anonymous image pulls, and a live TrueNAS health check. Record before/after benchmark results for a representative large library scan, an idle UI session, an active multi-job download session, and concurrent repeated TPDB lookups.

## Beta Acceptance Criteria

### Beta 1

- Status console is integrated.
- The ten scoped optimization stages are merged through separate pull requests with regression tests and measurements.
- Upgrade from 0.3.9 preserves all user data and secrets.
- All release-gate checks pass.
- Images are published only as `0.3.10-beta.1`; `main`, `latest`, and final `0.3.10` tags are untouched.

### Beta 2

- Beta 1 field defects are fixed and covered by regression tests.
- Performance measurements show no regression in download throughput, API latency, or scan correctness.
- All release-gate checks pass and images are published only as `0.3.10-beta.2`.

### Beta 3

- No known release-blocking defects remain.
- Upgrade, rollback documentation, and release notes are complete.
- All release-gate checks pass and images are published only as `0.3.10-beta.3`.

### Final 0.3.10

- Final code is identical to the accepted Beta 3 except for version and release metadata.
- The final release gate passes again before merging to `main`, tagging `v0.3.10`, or publishing stable images.
